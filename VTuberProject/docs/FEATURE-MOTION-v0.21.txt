状态：v0.21.0 实现与验证记录。
记录更新：2026-11-18。发布哈希与同步回执单独保存；本文不声称所有角度的美术问题已经解决。

本轮问题与范围

v0.20.1 已能连续转头，但相邻原画的鼻线、睫线、眼褶不一定被中性原稿的 RIFE 运动场准确对齐。闭眼画稿沿用中性运动场时，会出现两条鼻线、睫线重影；单纯增加过渡时间或增加相同类型的采样帧不能解决对应位置错误。

v0.21 在保留九方向 2D 原画的基础上，登记真实五官线条，把各方向、相邻表情的源像素映射到共同几何，再按原有连续头位组合。动作时序也保存实际显示的中间进度。未接入 3D、VTube Studio 或单图自动生成完整角色流程；表情仍依赖现有实际画稿。

来源与几何登记

运行登记：assets/short-hair-features-v1/manifest.json。
九方向：front、view-left、view-right、view-left-up、view-right-up、view-left-down、view-up、view-down、view-right-down。
共 180 个 chart：90 个眼图表（9方向×双眼×5状态）、81 个嘴图表（9方向×9状态）、9 个鼻图表。引用 81 个不同的源 PNG。每个姿态和每个 chart 均带 source/sourceSha256；加载时还核对当前表情登记的确切来源，不能仅凭图片名字或几何形状相似复用。

眼状态为 open、quarter、half、threeQuarter、closed。每方向每只眼的五状态使用相同完整睫线跨度，不能把逐渐缩小的眼孔宽度误作整只眼的宽度。横向有9个对应节点；每点登记 upper、lower 和独立 crease。上、下条带至少相隔2px，闭眼也保留可逆的2px几何支撑，这只是映射坐标，不会额外画出两条睫线。

810 个眼褶锚点中，519 个依据可见源线观测，291 个标明 inferred。遮挡或没有可见眼褶的位置不被宣称为真实绘画观测。观测段两端沿相邻观测点切线延伸，内部缺点线性插值；保持观测点和真实羽化校正点不动，并确保眼褶至少在 upper 上方2px。补全共290个端部点和1个内部缺点；11个位置受最小间距约束。它是隐藏区域几何补全，不是补画。

所有坐标在1122×1402原图空间。72个非open眼贴片的源rect与destination相同；18个open图表直接使用中性原稿坐标。已排除漏加源/目标矩形平移造成的系统性偏差。嘴部登记根据各自源/目标贴片的实际平移转到目标原图空间，不能照搬眼部的零平移假设。

一个真实合成例外：view-left/eyeLeft/quarter 的眼褶有节点落在贴片上边5px羽化区。节点2、3、4按“贴片×羽化 + 中性原稿×剩余权重”的实际主线校正，Y改变量约0.23、1.21、1.17px，并保留 creaseRegistration 来源说明。不要用未合成原稿的线条检测结果覆盖这些值。

鼻图表使用纵向9个非均匀节点：索引0–3为桥接段，4–8为主鼻线5点，索引4是主线起点。主线的对应关系不被上方长鼻梁拉伸。不同方向的可见鼻梁按源线登记；正面、正上、正下软阴影中心等缺少清晰线条的部分标记 inferred。横向支撑为主线两侧各1px。没有据此合成新的鼻线或遮挡下的鼻孔。

眉毛未接入新几何。已有眉样本受前发遮挡，无法为所有九方向建立可靠的隐藏轮廓与独立遮挡所有权。眉仍使用已有真实替换画稿和连续时间混合；不得把蓝灰发丝或遮挡边缘检测成眉线。

原PNG保持原字节，不重画、不擦线、不重新编码。2026-11-18 的独立源字节检查确认81个登记PNG均符合manifest SHA256，且与正式项目同路径文件字节相同。开发工作区证据：work/v021-face/source-byte-audit.json。发布前后全包文件摘要另见同步回执；validation/v0.21-source-byte-audit.json保留本次来源核对。

共同几何与运行采样

short-hair-feature-geometry.js 同时提供CPU映射与GLSL映射。目标图表按连续表情进度和头位重心权重生成。横向/纵向坐标按9个真实knots定位区间；垂直方向分 crease→upper、upper→lower 两段映射，条带之外保持平移延伸。nose不启用crease，mouth没有crease时也不会把默认值当作可见眼褶参与mask。

GPU几何纹理为12×42个RGBA浮点texel。每个feature占7行：target、A0、B0、A1、B1、A2、B2；曲线数据为[upper,lower,crease,knot]。头部信息包含轴向、范围、padding和快速bbox。来源slot为0–5。CPU mapFeaturePoint/featureSourceUVCPU 与相同结构用于验证节点、逆映射和边界。

鼻、眼、嘴的区域交接使用连续权重。眼区域覆盖鼻桥时给予眼线优先，避免被遮挡的鼻桥拉动眼睛。不能恢复为hard strongest/argmax选择某一条UV；那会在权重胜负交换处产生不连续。颜色采样先预乘alpha再组合，透明像素RGB不作为视觉误差的单独判据。

为什么扩大校正支撑

只对准主线而不给旧运动场中的错位线留足覆盖，会留下旁边的旧线尾巴。开发时对实际16边×7时刻RIFE场反求“哪个输出位置会采到源线”，使用来源权重≥0.1、反求残差≤0.15px的条件，共得到26,200个有效眼锚点。旧眼支撑 acrossCore=5、feather=12 时，部分错位线已落到几乎没有校正的羽化外缘；开放眼样本最大跨带偏移约19.82px，闭眼约13.37px。该分析只量化已登记锚点，不是全图美术质量分数。

因此目前鼻pads=[5,12,24,18]，眼pads=[8,14,22,16]，嘴pads=[3,9,4,10]；顺序为alongCore、alongFeather、acrossCore、acrossFeather。扩大的是完全校正核心，不只是让极弱羽化更宽。鼻主线旁的两条明显副线曾在扩大核心后实测消失，但不能据此宣布所有鼻梁和所有中间角度都已合格。

前发保护与残余菱形的追踪

五官区域扩大后更容易碰到前发。原有hairOwnership是已登记、不透明二值灰度PNG，运行时转成保护alpha并作半径x7/y3的矩形膨胀（实际核15×7），原PNG不变。每个来源分别检查旧RIFE UV及两端feature UV，防止把前发跟随眼睑拉动。

yaw=-0.45、pitch=-0.4、closed曾在画面左眼上方出现小菱形。改眼褶的inferred切线仍未消除它。2026-11-18 反查native约[371,506]：view-left/front/view-down权重为0.45/0.15/0.4；front的feature映射落到[401.738,486.146]的蓝灰发线，旧RIFE映射[402.734,490.028]则是皮肤。三个来源在新旧UV处的原保护mask都为0。实际源图证明它是漏保护的细发尖被眼图表变形，不是鼻线、眼褶检测偏差或坐标平移漏算。

已为front、view-left、view-down的该真实主发尖加入手审保护多边形，逐姿态查看五个眼状态，并带源hash。它只改变前景所有权，不擦除原画。开发证据：work/v021-face/foreground-protection-candidate.json、三个*-foreground-protection-review.png、diamond-trace-report.json、diamond-cpu-candidate.png。保护没有扩入缺乏证据的远处淡分叉或其他姿态。

保护需要平滑空间边界。把二值mask直接用于UV切换，即使纹理LINEAR采样，也可能在前发边界产生切片和折角；外侧连续衰减必须保持核心alpha=1，不能用模糊把真正前发核心削弱。CPU已比较保留核心后外衰减8px/12px：8px明显改善硬切片，12px进一步减弱眼线校正而收益有限。最终采用二值核心x7/y3扩张、外侧8px smoothstep衰减，核心保持255；缓存版本conservative-x7y3-strands-feather8-v3。最终GPU闭眼和threeQuarter对照确认硬切片改善，局部眼褶弯折仍列为限制。

19组CPU候选覆盖八个头位及open/quarter/half/threeQuarter/closed中的相关组合。闭眼小菱形明显改善，但部分half/threeQuarter在发尖和眼褶邻接处仍有局部弯折。保护共享复合像素可能牺牲局部眼线校正；CPU近似不包含全部Canvas2D、前发网格及GPU栅格细节，不能代替浏览器美术验收。开发证据：work/v021-face/protection-cases/（report.json、四张sheet、六组soft对照）。

四角表情合成

两个全局纹理“所有部位from / 所有部位to”无法正确表达独立眼、眉进度。眼贴片和眉贴片实际重叠，即使裁开patchOwner，一个像素仍可能已受两个贴片影响；单个t不能同时恢复两个部位的正确端点。此前联合眼眉检查24/30失败，不能退回这个结构。

当前每个姿态准备四个真实合成角：
A：眼/嘴from，眉from；B：眼/嘴to，眉from；
C：眼/嘴from，眉to；  D：眼/嘴to，眉to。

每像素执行mix(mix(A,B,tFace),mix(C,D,tFace),tBrow)。C与A共用face来源UV，D与B共用face来源UV。face面内只在eyeLeft/eyeRight/mouth中确定时间，brow面内只在browLeft/browRight中确定时间；两个面分别处理共同进度的全幅端点恢复。保留完整贴片union，不能再跨面裁开owner。面内已核对三个眼口贴片之间、两眉贴片之间不互相重叠。

三个sampler2DArray各装一个姿态的四个角，重复画稿按签名去重，避免增加一组GL→Canvas大画布往返。前发合成缓存保留四份输出，不能恢复成两份ping-pong后再统一上传，否则A/C或B/D会别名覆盖。未激活部位要规范为from==to,t=0；只把t设0但留下不同to会污染其他角。

连续动作与保存

short-hair-articulation.js 管理左右眼、嘴、左右眉五个独立部位的from/to/t。眼和普通张嘴沿五档相邻实际画稿前进；pucker/press/shiftLeft/shiftRight等特殊嘴型之间、不同眉分支之间经过neutral，不虚构从未画过的直连状态。

动作从实际已显示的fraction继续；途中反向、暂停、导入保存不能跳回最近离散状态。每帧先提出进度、绘制成功后提交；绘制失败或卡顿不积累不可见动作债务，不因补偿时间跨过整张相邻画稿。手动视线也连续推进；摄像头已有自己的滤波，记录片段重放不再套实时阻尼。

short-hair-studio-tracking.js 新录制clip v4保存实际显示的headPose、secondary三通道、22系数、五部位articulation和时间戳。最长60秒、1801样本、2MiB；到限保留可再打开的片段。兼容读v1/v2/v3。v4按记录时间插值头位、系数、微动和合法画稿路径，不能把记录的中间画面先量化再播放。工作台项目与独立输出传递实际articulation，而非仅传最近状态名。

保留RIFE4.25的原因与限制

继续使用已固定的Practical-RIFE v4.25模型和离线中性运动场。模型实现commit、权重SHA256、采样时间和场文件hash记录在assets/short-hair-motion-v1/manifest.json；构建方法见tools/RIFE-BUILD.txt。16组相邻原稿×7时刻＝112次既有离线神经推理；运行时不下载另一套模型，不逐直播帧做神经网络推理。

RIFE保留身体、头发及五官支撑之外的主要运动；它不是闭眼线条、鼻线与各独立表情的语义登记器。换一个通用补帧模型的名字不能替代实际来源对应、遮挡所有权和动作端点校验。本轮直接修正已确认的语义错位，未声称新的模型更优，也未把离线采样之间的字段插值描述成新的神经推理。

独立原稿形状仍有差异，三源内部组合也是两源场的几何扩展，不是声称RIFE本身预测了三个输入。遮挡下真实脸部、头发与眉毛的完整画师分层尚未自动补齐；所有线条质量仍需按实际角度观看。

后续维护不可回退的条件

1. 不退回两个全局from/to纹理配一个per-pixel时间；联合眼眉端点已经证明它不正确。
2. 不用hard strongest/argmax切换feature UV；需要连续的空间交接和前景保护。
3. 有可见眼褶的图表不得恢复为逐点upper-19。该值仅是includeCrease=false时的非活跃占位；眼褶隐藏点要继承已审查的切线/插值补全。
4. 不按眼孔宽度收缩整只眼的横向跨度；不同闭合状态保留完整睫线范围。
5. 不用单一全长线性Y把鼻梁和主鼻线混成一段；保留4桥接+5主线的非均匀节点。
6. 不直接重跑早期work/v021-prototype/build-features.py覆盖当前manifest；会丢失真实羽化校正、切线补全及后续保护数据。生成脚本若更新，必须保留来源审查和当前字段。
7. 不把端点像素一致、数值连续或测试数量当成美术重影全部解决。

最终验证 · 2026-11-18

自动测试：npm run check通过，npm test 1088/1088、0失败/取消/跳过，耗时21.775秒。第一次受限环境有12项HTTP监听因listen EPERM失败，允许本机监听后完整重跑全部通过。最终日志为validation/v0.21-check.txt、v0.21-tests.txt。包含CPU/GLSL图表、非均匀鼻节点、眼褶锚点、来源hash、坏数据拒绝、保护核心与衰减、动作反向/掉帧/绘制提交、clip v1–4、独立输出及裁切状态恢复等回归。

静态浏览器：919次绘制、747组比较。143原画端点和268表情端点极限逐像素一致；120姿态顶点最大原始RGBA差1。216三角形接缝在epsilon=1e-5时，预乘颜色/不透明区域最大差2，均符合可见像素门槛；原始RGBA全部216项超过2，最大255（透明RGB），不能标为原始RGBA全部通过。联合眼眉端点另60次绘制、30组比较，最大差1、0失败。最终静态数据是一轮完整检查，保存在30/60两个播放报告中，不重复累计成两轮。

保留的旧失败：validation/v0.21-feature-pre-protection.json中，保护修正前接缝可见最大差6、28组超过2；对最差8组追加56次epsilon收敛绘制，在1e-7时不透明最大1、预乘约1.083。最终8px外侧衰减后上述完整216组在1e-5已达到可见差2门槛。原始失败、收敛和最终报告均保留，未改写历史测量。

性能修改：WebGL画布仍是1122×1402，只对当前viewport执行scissor，清屏仍覆盖全画布，finally恢复状态。当前裁切减少约70.25%的片元区域，不等于帧率提高70.25%。C=A且D=B时复用已采样值；图表按部位混合，避免重复计算整组。12组头位/表情/微动、24次绘制，与全幅模式裁切读回逐像素一致（viewportRaster.exact=true）。

真实RAF并发动作：每段约8秒，连续转头、眼口眉、视线和微动一起运行；计时包括旧/新两套渲染、对比合成和细节放大。30fps请求：184次成功绘制，23.0671fps、平均35.528ms、最大帧隙99.335ms。60fps请求：233次成功绘制，29.0605fps、平均33.074ms、最大帧隙99.995ms。这是双画面诊断负载，不是单工作台或显示合成器测量。WebM实际解码分别134/118帧、时间跨度7951/7943ms、1560×680，不能称为真正30/60fps编码。报告：validation/v0.21-features-30.json、v0.21-features-60.json、v0.21-video-decode.json。

实际工作台：30与60fps请求各8/8转头通过，包含水平、斜向及中途反向，最大向量步长均0.10、保留中间姿态并精确到达终点。报告validation/v0.21-studio-turn-30.json、v0.21-studio-turn-60.json。报告version=0.20.1是沿用的验收模块版本；studioVersion明确为MoeMotion 0.21.0，非旧版测量。单工作台60请求的各段实测约48–60次绘制/秒；有冷纹理上传耗时尖峰，不承诺稳定60fps。

片段与输出实操：演示保存了23.0126秒、514样本的schema4片段，导入后成功重放至13.2秒，手动切换停止（没有声称整段完整播放）。独立输出late join，工作台显示1个接收窗口，输出页显示直播画面已连接并绘制当前角色；保存截图。透明设置开启，alpha和传输另有自动回归；未用截图冒充透明通道数值检查。未开启真人摄像头、麦克风或实际OBS；长期丢帧、OBS设备性能仍需实机验证。
